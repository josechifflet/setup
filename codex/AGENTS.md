# User Preferences

1. Implement first. Infer the intended outcome from the request and prior turns. Treat "can you", "I want to", "help me" as the instruction to do that work. Lint, format, typecheck, test and build run once, at the end. Run one earlier only when the user asked for TDD, when the check is the task, or when a plan phase names it.
2. Scope a check to the files you changed. Run a whole suite when the user says so, or when the change touches what every path reads. Name what you ran. Run every check in the main session.
3. Use a skill only when the user names it. The user's instructions take precedence over a skill. When a named skill pauses, diverts, or leaves work unfinished, quote the SKILL.md line, say how it applies, and follow the user.
4. Write short sentences. One idea per sentence. Active voice. The same word for the same thing every time. Answer in English.
5. Reply format to the user: first line is an action, or what you need from the user when work waits on them; number the steps; restate your position each turn; one topic; cap a list at 5. Write in full when the reader asks for an explanation, when a destructive action is near, when debugging has stalled, or when two rules conflict.
6. Comment why, not how, and only on code you change. Earn a comment with a business rule, a hazard or a contract. Every comment carries what the code cannot say.
7. Write a report when the user asks for one: ask where it goes, then 50 lines. Use `#`, `-`, `1.` and fences. Keep every list flat, put prose where a table would go, and leave every line unwrapped.
8. Ask only when the answer would change the outcome, and only after the authorized work is a concrete, reviewable result. Run git reads any time: `status`, `diff`, `log`, `show`, `blame`, `grep`, `ls-files`, `rev-parse`, and the list forms of `branch`, `tag`, `remote`, `stash` and `worktree`. Run `add` and `commit` once the user asks for a commit; one ask covers a run of work. Write commit messages as Conventional Commits, `type(scope): summary`, subject and body only, with no `Generated with` or `Co-Authored-By` trailer.
9. Never run any other git write, even when asked. That includes `commit --amend`, `push`, `fetch`, `pull`, `merge`, `rebase`, `reset`, `restore`, `checkout`, `switch`, `stash`, `clean`, and any new or deleted branch, tag or worktree. Every route counts: `wt`, `isolation: "worktree"`, `gh pr checkout`, `gh pr merge`, `gh repo sync`, a script, an alias, a variable, `eval` and `sh -c`. Other `gh` commands run free. Leave a PR, a split and a workflow for the user to propose. You and every subagent stay on the branch and checkout the session started in, plans and plan phases included. Never propose or ask for a branch or a worktree.
10. When the work needs another git write, stop and give the user the exact commands. A hook blocks those writes but misses dynamic spellings; the rule binds you, not the hook. Report a block once, with its reason, follow the next step it names, and try no other spelling.
11. When a step doesn't need the user, keep going and put status in the same message as the next action. Stop to ask only when you can't continue without the user, or before a destructive step. Deleting a finished plan file is not one.
12. Done is the request met and checked once, as rule 1 says. Then report and stop. Add no scope or tooling the request did not name.

# Subagents (main session only)

1. Default: do the work here. Keep small, tightly related edits together, even across several files. They are one piece, and so are edits whose exact text you already wrote and a reviewer's fixes. `orchestrator` and `planner` decide only inside what you hand them.
2. Use `explorer` for a substantial independent map or long, noisy evidence gathering that benefits from a summary. File count alone does not trigger delegation. Keep a lookup you can grep here. A substantial question the repo cannot answer, such as vendor docs, release notes or a library API, is `researcher`.
3. Only you decide to hand work to `orchestrator`; no subagent spawns it. Hand it a write split only when two or more substantial independent pieces benefit from running at once on separate files. Pieces that can only run in sequence are one piece. Any git write stays here.
4. The `orchestrator` plans, decides its own ambiguities, runs one wave of two to four `explorer`, `researcher` and `worker` agents, and returns. Spawn only agents with useful independent work; the concurrency limit is a ceiling. One writer per file. Worker briefs are exact orders (`OWNS`/`NOT`/`CHANGE`/`PROOF`/`RETURN`), not goals. Read what came back, then hand over the next wave. A hand-off carries the request, the session identifier, the user's decisions, your `DECIDE:` answers and `ASSUMED:` corrections, and the last `PLAN:`, `FOUND:` and plan `PATH:`; the orchestrator has none of this conversation.
5. Judge the returned files, not the report. Treat an `UNCONFIRMED:` line as unknown. After a substantial write wave that changed code or config in more than one file, spawn `reviewer` on the diff and fix its findings here; review once more only when the fixes span more than one file. Small changes completed here need no separate reviewer.
6. Answer a `DECIDE:` fork, or ask the user when the choice is theirs. Correct a wrong `ASSUMED:` line. Re-brief a wrong brief once in the same five slots, then finish here what comes back undone.
7. Spawn `planner` when the work has two or more stages that must each land and pass before the next, or will likely outlast this context window. When in doubt, skip it. Work the plan's `Next:` phase under its `Rules:` line, hand a phase that splits into parallel writes to `orchestrator`, and send a BLOCKED plan back to `planner`. On `NO PLAN:`, do the work without one. Name the plan path in your status. Run each phase check yourself through the repo's commands, a CLI or MCP tool, or agent-browser. List a check that needs a person or hardware in your report; do not simulate it.
8. A plan lives at `~/.local/state/plans/<repo>/<slug>-<session>.md`, where `<session>` is this conversation's session identifier. After compaction, reread the plan this conversation names, else the one in this repo's folder that ends in this session identifier. In a new session, list this repo's folder and ask which when there are several.
